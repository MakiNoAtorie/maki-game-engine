|---|---|---|---|

| GPU time in Tracy | The pass zones in Tracy show CPU time (recording of commands). GPU times are in the stats panel and in `bench.csv` only. | Profiling needs GPU zones on the Tracy timeline | Tracy shows a GPU zone for each pass. |
| Mesh buffers in GPU-only memory | The normal buffers and the mesh table are CPU-writable. The gpu crate has no buffer-to-buffer copy. On the RTX 5060 Ti a GPU-only normal buffer gave no gain (`docs/perf-improve.md`, section 11). | Another GPU, or a scene with more than 200 MB of mesh data, shows a loss | Mesh buffers are GPU-only. Validation is clean. |
| Owner of the meshes of a model | `Assets<Model>::remove` leaves the meshes of the model in the mesh store: the caller removes them. `load_requested_room` does that for each model that the next room does not name (`RoomModels`). The player model has no such owner: it stays loaded for the rest of the run. | A model has an owner other than a room | `Assets<Model>::remove` removes the meshes itself, or a model has a reference count. |
| Asynchronous loading | `load_gltf` and `Textures::load` read and decode the file before they return, and the mip levels are made on the CPU at the upload. The room loader and the player already wait for `LoadState::Ready` (`spawn_loaded_models`, `attach_player_model`). A mesh table entry is written one time: a texture that arrives after its mesh would not show. Measured: the first frame of the textured test room (8 textures of up to 64 x 64 pixels) takes 27.7 ms for the load, that of room A 27.6 ms. | Stage that adds a loader thread, or a room with large textures | A model shows some frames after start, then its textures. The room loader did not change. |
| Mesh table size | Fixed at `MAX_MESHES` (1024). A mesh past the limit is not uploaded; an error is logged. | A scene needs more meshes | The table grows. Shaders read the new table. |
| Mesh shared by many glTF nodes | The loader makes one mesh for each node, with the node transform applied to the vertices. | A model file makes this expensive | One mesh, many instances, each with the node transform. |
| Buffer usage flags | Every buffer permits all uses of the crate (storage, copy, acceleration structure input and storage). The UI vertex data needs no other use: the vertex shader reads storage buffers. | A use has a cost or a limit | `BufferDesc` has a usage field. Validation is clean for each usage. |
| BLAS build stops the game | `Gpu::create_blas` submits the build and waits until the GPU queue is idle. One wait for each mesh group. A room change with generated meshes took 2 ms (`trip_720p`, column `room_load_ms`), and the first load 29 ms. No room has a model file. The editor loads the room again for each change that is not a light or the pose of a prop (`maki_scene::patch_room`): while such a value is dragged, each frame builds each mesh of the room again, and the picture starts again. | A room has a large model file, or a drag in the editor is not smooth | The build is recorded in the frame. No frame is longer at a room change. The editor builds only the mesh that changed. |
| BLAS compaction | A BLAS keeps the size of the first estimate. | A scene uses much GPU memory for meshes | The BLAS is copied to its compact size. Memory use is lower; the picture is the same. |
| TLAS size | Fixed at `MAX_INSTANCES` (4096). More instances are not drawn; an error is logged one time. One TLAS for the life of the `Gpu` (no `destroy_tlas`). | A scene needs more instances | The TLAS grows. Validation is clean. |
| Part of a model that moves alone | The player and the door move: each is its own mesh, so its own BLAS, and the TLAS is built again in each frame with a change. All meshes of a model share one BLAS: a mesh instance of a model draws the full model, so one mesh of a model cannot move alone (a warning is logged). The player model of the config (`player_model_path`) uses this: one instance of its first mesh draws the model. | A model has a part that moves (a character with a held object), or a model must show in part | The part moves alone. No warning. |
| Instance with a scale or rotation | The shader turns the normal with the world-to-object matrix. The two mirrors of the test scene are a cube with a rotation and a non-uniform scale; their reflections are correct. The normals of a cube are along its axes, where a wrong matrix for a non-uniform scale does not show. | A scene has a scaled object with slanted or round faces | The lighting of the object agrees with its shape. |
| Many lights | The trace pass puts up to `MAX_LIGHTS` (256) lights in a buffer. The shader picks one of 8 candidate lights for each shadow ray, and tests each light sphere against each ray that can show a light. Measured with 9 lights. | A scene has some hundreds of lights | The light spheres are in the TLAS, and the pick uses reservoirs over frames (`docs/perf-improve.md`, D5 step 3). |
| Shadow edge on low-polygon round meshes | The shadow ray starts from the true triangle, the light angle uses the smooth normal. On a coarse sphere the dark side can start with a stepped edge. Not visible on the default sphere (32 x 16). | A coarse round mesh is in a scene | The edge between the light side and the dark side is smooth. |
| Light by way of a mirror or through glass (caustics) | Shadow rays find only light that comes straight from the light, and glass stops a shadow ray. Light that reaches a diffuse surface by way of a mirror or through glass comes only from a bounce ray that finds the light by chance. `indirect_clamp` (stage 15) limits such a sample: no speckle, and the light is too dark (the spot under the glass ball is almost gone; the picture of the test room has 2.8 % less light). | A stage that samples these paths (photon map, manifold sampling, light by way of a flat mirror as a virtual light) | The floor in front of a mirror and the spot under the glass ball are as bright as with `indirect_clamp = 0` at 65536 samples, and clean at `max_samples`. |
| Material kinds from glTF | The loader selects one of five kinds (diffuse, mirror, glass, metal, plastic) from the metallic, roughness, and transmission factors, and reads the emissive factor (`material_kind` in `crates/assets/src/model.rs`). Since stage 25 it reads the base color texture, the emissive texture, and the alpha mode. A surface that is partly metal or partly clear shows as one kind: no metallic-roughness texture. No emissive strength extension. Tested with generated files only. | A file from a modelling tool with metal, plastic, and glass parts is at hand | The parts look as they do in the tool. |
| Rough surfaces later on a path | Metal and plastic have their reflection only where the pixel shows them (also behind a mirror or glass). After a bounce, and in the reflection on glass, they count as diffuse with their base color: a metal object gives the room a little too much soft light and no bright spots, and it looks dull in a glass reflection. | A scene shows it (a room with much metal) | Later surfaces keep a reflection with a higher roughness, and the picture has no new bright speckle. |
| Light of a mesh | A surface with a light of its own (an emissive color, since stage 25 also an emissive texture) lights the room by bounce rays that find it by chance, with the limit `indirect_clamp` for each ray: a small or very bright one gives noise and too little light. | A room needs a lit sign or a screen as a light source | Shadow rays aim at such meshes (a light list of triangles; with many of them: reservoirs, ReSTIR DI). |
| Cone light from behind | The sphere of a cone light shows black from a direction out of its cone, and hides what is behind it. | It shows in a room | The sphere of a cone light does not show from behind, or has a dim body color. |
| Cost of the path state | Stage 21 made the trace pass 17 to 22 % slower, also in a scene with no rough material (`s21c` against `s19`): the loop has more values that stay alive over each ray. `heavy_mixed_lights8_1080p` is at 7.3 ms of the 8 ms budget. Stage 25: textures cost 1.9 % of the trace pass and textures with holes 3.4 % more for all rays of a scene that has them (the code alone, in a scene where no ray uses it); a scene with no texture runs a shader without the code. | The budget is short | The values of the rough reflection are packed, or a second pipeline traces scenes with no rough material. |
| Path length limit | A path stops after `max_path_rays` rays (config, default 12). A mirror or glass surface at the last ray counts as diffuse and gets direct light. The test scene has no place where this shows. | A scene has mirrors that face each other, or glass in many layers | The default is chosen with an error metric and screenshots (`docs/perf-improve.md`, R4 step 3). |
| Bounce light of points that the picture does not show | `bounce_light` reads the bounce light of a point from the picture of the frame before. A point that the picture does not show (the near walls that the camera looks through, the back of objects, all that is behind the camera) has none: a bounce ray that ends there brings direct light only. Against a reference with 8 bounces the error is 0.0014 (rest, room A) with the default `max_bounces = 2`; with one bounce it is 0.013, and with one bounce and no `bounce_light` it was 0.029. The second bounce costs a ray: the heavy benchmark scene is at 9.3 ms, over the budget of 8 ms at 1080p. | The dark side of a room is too dark, or the frame time must go down | A cache in world space (a hash grid of cells, GI-1.0 or SHaRC) holds the bounce light of each surface, and `max_bounces = 1` with the cache is as near to the 8-bounce reference as two bounces are now. |
| Glass in glass, camera in glass | The glass code takes air as the other side of each glass surface. No test with two glass meshes that overlap, or with the camera in a glass mesh. | A scene has such a case (a drink in a glass) | The picture agrees with a reference renderer. |
| Reflections of things that move | Behind a mirror or glass, `motion` is that of the point at the path length along the camera ray, with the camera of the frame before: correct for a flat mirror and a scene at rest. For an object that moves in a mirror, and for all that shows through a glass ball while the camera moves, the temporal pass reads the history of another point; its surface test rejects it or not. | A scene shows a trail in a mirror | The motion of a pixel behind a mirror uses the transform of the instance in the frame before, mirrored. |
| Mirror behind a mirror | The normal of a pixel behind mirrors is mirrored at the first mirror only. Behind two mirrors the filter takes each pixel for a surface of its own: no blur, more noise. | Two mirrors face each other in a room | The trace pass keeps a matrix for all mirrors on the way. |
| Light inside glass | On the way from the camera to the surface behind glass, only the first glass surface reflects (a second path, `specular`). The reflection path ends at its first diffuse surface: the room in the reflection has direct light only. | A glass object looks wrong against a reference renderer | The path also follows the reflection inside the glass, or takes it at random with a stable surface for the denoiser. |

| Anti-aliasing in motion | The pass `taa` gives smooth edges at rest (sharpness 0.93 against a reference with the mean of all jitter points).
