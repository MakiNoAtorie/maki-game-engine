# Open items

Items that cannot be tested yet. Each item names the stage that makes the test possible. Remove an item when its check passes.

| Item | State now | Testable when | Check |
|---|---|---|---|
| Swapchain image views | Not created. The frame reaches the swapchain by blit only: the UI pass draws into the `output` image, before the blit. | A pass must draw straight into the swapchain image | Views are built again on resize. No leak at shutdown. |
| Textures from glTF | `Gpu::write_image` copies pixels into an image; the UI uses it for the font image. The glTF loader reads no textures. | Stage that adds glTF textures | A texture from a glTF file shows correctly through a sampler. |
| Missing-feature error path | Code is written. This GPU has all features, so the path did not run. | A GPU or driver without ray query is available | The game stops with a message that names the GPU and each missing feature. |
| Other GPUs and systems | Tested only on an NVIDIA RTX 5060 Ti, Windows 11. | AMD, Intel, or Linux hardware is available | The room and the model show in normal colors, resize works, validation is clean. |
| Swapchain surface fallbacks | Code is written for a non-opaque composite alpha mode and for a surface without a fixed extent. Windows uses neither. | Linux (Wayland) is available | The window shows the frame and resizes. |
| Buffers and the TLAS in the frame graph | Passes declare images only. `Gpu::build_tlas` records its own barriers against compute shaders. No pass shares a buffer with another pass. | A pass writes a buffer that a later pass reads | The graph records the buffer barrier. Synchronization validation is clean. |
| Graphics pipeline state | `GraphicsPipelineDesc` has one fixed state: triangles, no depth test, no culling, premultiplied alpha blend, no vertex buffers. Only the UI pass uses it. | A second graphics pass needs another state (debug lines, depth test) | The description has the new field. The UI still shows correctly. |
| Keyboard capture by the UI | `InputCapture::keyboard` stops key actions while a text field of egui has the focus. No panel has a text field, so only the unit test of the platform crate ran this path. The mouse path ran in the game (wheel on a panel). | A panel has a text field | Typing in the field moves no light and does not quit. |
| egui features that are off | No clipboard, no link opening, no accessibility tree (`egui-winit` without default features). Paint callbacks and user textures are not drawn. Each texture uses one linear sampler; `TextureOptions` is not read. | A panel needs one of them | The feature works in the panel. |
| Display scale other than 100 % | egui takes the scale from the window. Tested only at 100 %. | A display with another scale is available | Panel text is sharp and has the size that the OS scale gives. Clip rectangles are correct. |
| Tracy zones | Each schedule and each frame graph pass runs in a `tracing` span; the `profile` feature sends them to Tracy. The build and a run with the feature are clean, and the spans show in the log at `MAKI_LOG=trace`. No Tracy server was connected. | A Tracy server is at hand | Tracy shows one zone for each schedule and each pass in each frame. |
| GPU without timestamp queries | `Gpu::write_timestamp` does nothing and `FrameGraph::timings` stays `None`; the benchmark then writes `cpu_ms` only, after 8 more frames. This GPU has timestamps, so the path did not run. | Such a GPU or driver is available | The game runs. `bench.csv` has the `frame` and `cpu_ms` columns. |
| GPU time in Tracy | The pass zones in Tracy show CPU time (recording of commands). GPU times are in the stats panel and in `bench.csv` only. | Profiling needs GPU zones on the Tracy timeline | Tracy shows a GPU zone for each pass. |
| List of panels | A closed panel opens again only from code (`Panels::toggle`; the help panel has an action). | Panels crowd the screen | A menu shows one checkbox for each registered panel. |
| Mesh buffers in GPU-only memory | Mesh buffers are CPU-writable. The gpu crate has no buffer-to-buffer copy. | Stage that adds a staging upload to the gpu crate | Mesh buffers are GPU-only. Validation is clean. |
| Mesh removal in the game | `GpuMeshes::sync` frees the buffers and the BLAS of a removed mesh. No game code removes a mesh. The buffer path ran one time in a temporary test in stage 5 (remove, upload again, validation clean). The BLAS path (`Gpu::destroy_blas`) did not run. | Stage with dynamic objects or scene change | A mesh is removed during play. Its table index is used again. Validation is clean. |
| Owner of the meshes of a model | `Assets<Model>::remove` leaves the meshes of the model in the mesh store. | Stage that unloads a model | The model and its meshes are gone from the stores and from the GPU. |
| Asynchronous loading | `load_gltf` reads the file before it returns. Callers already wait for `LoadState::Ready`. | Stage that adds a loader thread | A model shows some frames after start. `scene.rs` did not change. |
| Mesh table size | Fixed at `MAX_MESHES` (1024). A mesh past the limit is not uploaded; an error is logged. | A scene needs more meshes | The table grows. Shaders read the new table. |
| Mesh shared by many glTF nodes | The loader makes one mesh for each node, with the node transform applied to the vertices. | A model file makes this expensive | One mesh, many instances, each with the node transform. |
| Buffer usage flags | Every buffer permits all uses of the crate (storage, copy, acceleration structure input and storage). The UI vertex data needs no other use: the vertex shader reads storage buffers. | A use has a cost or a limit | `BufferDesc` has a usage field. Validation is clean for each usage. |
| BLAS build stops the game | `Gpu::create_blas` submits the build and waits until the GPU queue is idle. One wait for each mesh. | A mesh is uploaded during play (loader thread, dynamic objects) | The build is recorded in the frame. No frame is longer at an upload. |
| BLAS compaction | A BLAS keeps the size of the first estimate. | A scene uses much GPU memory for meshes | The BLAS is copied to its compact size. Memory use is lower; the picture is the same. |
| TLAS size | Fixed at `MAX_INSTANCES` (4096). More instances are not drawn; an error is logged one time. One TLAS for the life of the `Gpu` (no `destroy_tlas`). | A scene needs more instances | The TLAS grows. Validation is clean. |
| TLAS with no instance | `build_tlas` permits an empty list. The scene always has the room, so the path did not run. | A scene can be empty (scene change) | The screen is black. Validation is clean. |
| Moving instance | The TLAS is built each frame from the extracted transforms. `extract_instances` asks for an accumulation reset when an instance is new, written, or removed. No entity moves, so only the "new" path ran. | Stage with dynamic objects | An object moves on the screen and the picture starts again. No renderer code changed. |
| Instance with a scale or rotation | The shader turns the normal with the world-to-object matrix. The two mirrors of the test scene are a cube with a rotation and a non-uniform scale; their reflections are correct. The normals of a cube are along its axes, where a wrong matrix for a non-uniform scale does not show. | A scene has a scaled object with slanted or round faces | The lighting of the object agrees with its shape. |
| Depth, normal, and motion images | The trace pass writes them. No pass reads them. Motion is all zeros. The camera ray has a random position in the pixel, so depth and normal change a little from frame to frame at edges. They are not written when the accumulation is complete. | Denoiser or upscaler stage | A pass reads them by name. Motion vectors agree with a moving object. |
| Single-sided parts of a model | Camera rays cull back faces, to look into the room through the near walls. A generated glTF pyramid showed correctly (temporary test). No model with single-sided parts was tested. | A glTF file with single-sided parts (leaves, cloth) is at hand | The parts show from the two sides, or the cull is limited to the room. |
| Two cameras | The first `Camera` entity is used. | The game needs a second camera (editor) | A marker selects the active camera. |
| More than one light | The game can spawn many `Light` entities and all are extracted. The trace pass sends the first one to the shader, in push constants. | A scene needs a second light | The lights are in a GPU buffer. Each shadow ray picks one light at random. The picture has the light of all lights. |
| Accumulation reset on removal | `extract_camera`, `extract_lights`, and `extract_instances` read `RemovedComponents`. No game code removes a camera, a light, or a mesh instance. | Stage with dynamic objects or scene change | An entity is despawned. The picture starts again in the same frame or the next one. |
| Linear filter on the accumulated image | The tonemap pass samples the `Rgba32Float` accumulated image with a linear filter. Vulkan does not require this filter for 32-bit float formats; the gpu crate does not check it. | A GPU without the feature is available | Validation is clean, or the game stops with a message that names the missing feature. |
| Light motion between fixed steps | The light moves in `FixedUpdate` only. With a frame rate equal to `fixed_hz`, a frame can have 0 steps and the next one 2: the light then moves in each second frame. `Time::alpha` is not used. | Stage that interpolates simulation state for the renderer | The light moves in each frame at each phase of the frame clock. |
| Shadow edge on low-polygon round meshes | The shadow ray starts from the true triangle, the light angle uses the smooth normal. On a coarse sphere the dark side can start with a stepped edge. Not visible on the default sphere (32 x 16). | A coarse round mesh is in a scene | The edge between the light side and the dark side is smooth. |
| Light by way of a mirror or through glass (caustics) | Shadow rays find only light that comes straight from the light, and glass stops a shadow ray. Light that reaches a diffuse surface by way of a mirror or through glass comes only from a bounce ray that finds the light by chance: bright speckle that is still visible at 2400 samples. | Denoiser stage, or a stage that samples these paths (clamp, photon map, manifold sampling) | The floor in front of a mirror and the spot under the glass ball are clean at `max_samples`. |
| Materials from glTF | `Material` (diffuse, mirror, glass) is set in code with `Mesh::with_material`. The glTF loader reads the base color only; each loaded mesh is diffuse. | Stage that reads glTF materials (metallic, roughness, transmission) | A glTF file with a metal part and a glass part shows them as such. |
| Path length limit | A path stops after 12 rays and brings no light. The test scene has no place where this shows. | A scene has mirrors that face each other, or glass in many layers | The dark area is small, or the limit is a config value. |
| Glass in glass, camera in glass | The glass code takes air as the other side of each glass surface. No test with two glass meshes that overlap, or with the camera in a glass mesh. | A scene has such a case (a drink in a glass) | The picture agrees with a reference renderer. |
